What this one optimises for

  • The tree is the filesystem. What you see is what a teammate sees after a git pull, with no mapping to learn.
  • The destination is drawn in the tree itself: a dashed row sits at the exact path Approve will write, and the header button repeats it.
  • static/ is what you design and approve. dynamic/ is regenerated from code after implementation, so those entries are read-only and carry a freshness mark instead of a count.
  • Best when the team already thinks in paths and reviews these files in pull requests.

Where the layout is stored

  • Hand-placed positions go to .doppel/layout/<diagram>.json, committed with the repo, so everyone opens the diagram arranged the same way.
  • It sits outside architecture/ on purpose: steering feeds that whole folder to Kiro as approved design, and pixel coordinates are not design.
  • Keyed by element id, not by position in the file, so a rename or reorder does not scramble anyone's layout.
